# Deploying to the DreamHost VPS (Managed VPS + Proxy Server)

Run these in order, over SSH, on the VPS.

> **This replaces the original Apache-vhost/certbot plan.** This account is a
> *Managed* DreamHost VPS (`vps21367.dreamhostps.com`) — the shell user has no
> sudo, and Apache's real config is generated by the DreamHost panel, not by
> hand-edited `/etc/apache2` files. There is also no Passenger/Node option on
> the domain's own Settings page. The actual supported path is DreamHost's
> **Proxy Server** feature: Panel → Servers & Usage → Manage → Proxy Server →
> point `manage.shopq.lk` at a local port (8000–65535) on this VPS. DreamHost's
> proxy requires the app to bind `0.0.0.0`, not `127.0.0.1`. SSL for
> `manage.shopq.lk` is already provisioned by DreamHost's panel (the domain
> already terminates HTTPS on this box) — there is no certbot step to run here.
>
> For the investigation that led to this (Managed-VPS check, Passenger
> compatibility, panel walkthrough) see `HANDOVER-manage-shopq-lk.md`.
>
> **This VPS has 1GB RAM and no swap.** Do not run `next build` on it — it
> will OOM-kill. Build locally (or in CI) and ship the `.next` output instead.
> `pm2 startup` also needs root, which this shell user doesn't have — use a
> user crontab `@reboot` entry for reboot persistence instead.
>
> DreamHost's **Web Application Firewall** is enabled on this domain. If you
> see unexplained 403s on PUT/DELETE or on JSON request bodies after
> deploying, that's the likely cause — blocked requests never reach the app,
> so they won't show up in `pm2 logs`. Ask whoever has DreamHost panel access
> to disable it if this happens.

## 1. Check Node, install if missing/too old

```bash
node -v
```

Need 18.18+ (20 LTS recommended) — this is a **Next.js** app (`next start`),
not Express. If Node is missing or older, install a user-scoped Node via nvm —
this does **not** touch any system-wide Node another app on the box might
already depend on:

```bash
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.39.7/install.sh | bash
source ~/.bashrc
nvm install 20
nvm use 20
```

## 2. Install PM2

```bash
npm install -g pm2
```

DreamHost's proxy only routes traffic to the port — it does not supervise the
process. PM2 is what restarts the app if it crashes or the server reboots.

## 3. Get the code onto the server (SSH deploy key, read-only, scoped to this one repo)

```bash
ssh-keygen -t ed25519 -f ~/.ssh/shopq_admin_backend_deploy -N ""
cat ~/.ssh/shopq_admin_backend_deploy.pub
```

Copy that output, then on GitHub: `ggohulan/shopq-ecom-backend` → Settings →
Deploy keys → Add deploy key → paste it, leave "Allow write access"
**unchecked** (read-only — this key can never push).

```bash
chmod 600 ~/.ssh/config ~/.ssh/shopq_admin_backend_deploy
cat >> ~/.ssh/config << 'EOF'
Host github-shopq-admin-backend
  HostName github.com
  User git
  IdentityFile ~/.ssh/shopq_admin_backend_deploy
EOF
git clone github-shopq-admin-backend:ggohulan/shopq-ecom-backend.git ~/shopq-admin-backend
cd ~/shopq-admin-backend
```

Clone it outside the web root (`~/manage.shopq.lk` is DreamHost's static
docroot for the domain and is unrelated to this — leave it alone).

## 4. Create `.env.local`

DB credentials come from whoever created the database (in phpMyAdmin) —
paste them directly here, not over chat. Generate the JWT secret on the
server itself:

```bash
openssl rand -hex 32
```

```bash
cat > .env.local << 'EOF'
DB_HOST=<your DreamHost MySQL hostname, e.g. mysql.shopq.lk>
DB_PORT=3306
DB_USER=<db user>
DB_PASSWORD=<db password>
DB_NAME=shopq_supplemental
DB_SSL=false
ADMIN_JWT_SECRET=<paste the openssl output here>
ALLOWED_ORIGIN=https://shopq.lk
LARAVEL_API_BASE_URL=https://shopqhub.com/api/v1
EOF
chmod 600 .env.local
```

## 5. Build locally, not on the server

On the machine you develop on (not the VPS):

```bash
npm ci
npm run build
```

This produces `.next/`, which is the only heavy artifact — it's what gets
shipped. `.next` is gitignored, so it doesn't come across in step 3's `git
clone`; transfer it separately, e.g.:

```bash
scp -r .next <ssh-user>@<vps-ip>:~/shopq-admin-backend/
```

## 6. Install runtime deps and start under PM2

Back on the VPS, in `~/shopq-admin-backend`:

```bash
npm ci --omit=dev
pm2 start deploy/ecosystem.config.js
pm2 save
pm2 logs --lines 50   # confirm it connected to MySQL and isn't crash-looping
```

`npm ci --omit=dev` only installs `node_modules` — it does not run a build
(there's no `prepare`/`postinstall` build hook in `package.json`), so it's
safe on 1GB RAM. `npm start` is `next start -p 8001 -H 0.0.0.0` (set in
`package.json`) — port 8001 and the `0.0.0.0` bind are both required by
DreamHost's Proxy Server.

Confirm it's actually listening:

```bash
curl -I http://127.0.0.1:8001
curl -I http://0.0.0.0:8001
```

**Do not continue past this point until that returns a real response.**

Since `pm2 startup` needs root (unavailable here), set up reboot persistence
via a user crontab instead — find PM2's full binary path first, since cron
runs with a minimal `PATH`:

```bash
which pm2   # note the full path, e.g. ~/.nvm/versions/node/v20.20.2/bin/pm2
crontab -e
```

Add a line (using the full path from `which pm2`):

```
@reboot /home/<user>/.nvm/versions/node/v20.20.2/bin/pm2 resurrect
```

## 7. Add the proxy in the DreamHost panel

This is a panel action, not a shell command — the repo owner or whoever has
DreamHost panel access does this:

Panel → **Servers & Usage → Manage** (on `vps21367`) → **Proxy Server** →
enter `manage.shopq.lk`, port `8001` → **Add Proxy**. It returns a 502 until
the app is listening — that's expected and confirms the proxy itself is
working.

Two things this changes, both already checked against this app:

- **Static assets**: Next.js serves its own `_next/static/*` bundles from the
  same process on the same port, so there's nothing split across origins —
  DreamHost's static-asset caveat doesn't apply here.
- **`.htaccess`**: this app doesn't use one, nothing to migrate.

The domain's HTTPS (Automatic HTTPS) is already provisioned by DreamHost's
panel independently of this — once the proxy is added, `https://manage.shopq.lk`
should reach the app directly. No certbot step is needed or possible on this
account.

## 8. Verify

```bash
curl -I https://manage.shopq.lk
curl https://manage.shopq.lk/api/site-offer
```

Both should succeed. If a write endpoint (PUT/DELETE, or any JSON POST/PUT
body) comes back with an unexplained 403 that never shows up in `pm2 logs`,
that's DreamHost's WAF intercepting it before it reaches the app — ask
whoever has panel access to disable it for this domain.

Once verified end-to-end: confirm DNS for `manage.shopq.lk` actually points
at this VPS (`dig +short manage.shopq.lk`, controlled from Vercel's domain
settings since Vercel hosts `shopq.lk`'s DNS), and tighten DreamHost's MySQL
"Remote Hosts" from `%` to this server's specific outbound IP.
