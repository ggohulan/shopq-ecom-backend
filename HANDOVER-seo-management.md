# Handover: SEO management section

*Written 28 Sep 2026, after a scoping discussion with the project owner. Not built — this is a
spec for a developer to implement, following the patterns already established elsewhere in this
codebase this session (Products/Reviews/Promo Banners).*

---

## 1. What this is, and why it lives here

This backend is becoming the source of truth for everything about a product/page that isn't core
inventory data (see Products, Reviews, Promo Banners - all follow the same shape: this backend
owns the data, the storefront reads it via a public GET endpoint and renders it). SEO metadata
follows the same pattern: **this backend stores it, the storefront reads it and renders the actual
`<title>`, `<meta>`, and JSON-LD tags.**

No SEO tooling exists today - this is a general gap, not a fix for a known ranking problem.

**Scope for v1:** products, category pages, and static pages (home, about, etc. - inventory the
actual static routes on the storefront before starting; this backend has no visibility into that
project). **Explicitly out of scope for v1:** a redirects manager (old URL → new URL) - add later
if a real need shows up.

## 2. Data model

One table, keyed by what kind of page it's for and which one:

```sql
CREATE TABLE IF NOT EXISTS seo_meta (
  id             INT AUTO_INCREMENT PRIMARY KEY,
  entity_type    ENUM('product', 'category', 'page') NOT NULL,
  -- product_id for products (matches product_content.product_id elsewhere in this schema),
  -- category slug/id for categories, a fixed key (e.g. 'home', 'about') for static pages.
  entity_id      VARCHAR(64) NOT NULL,
  meta_title     VARCHAR(70) NULL,
  meta_description VARCHAR(160) NULL,
  og_image_url   VARCHAR(500) NULL,
  canonical_url  VARCHAR(500) NULL,
  is_noindex     TINYINT(1) NOT NULL DEFAULT 0,
  updated_at     TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY idx_entity (entity_type, entity_id)
);
```

70/160 char limits match Google's typical title/description truncation points - worth showing a
live character counter in the admin form, not just enforcing at the DB layer.

**Fallback rule, important for the storefront side:** an empty `meta_title` falls back to the
product/category/page's own name; an empty `og_image_url` falls back to the product's primary
photo. That fallback already exists and is queryable - see `product_images.is_primary` and
`GET /api/product-images?productId=` (`src/app/api/product-images/route.js`). Don't duplicate that
image-picking logic; call the existing endpoint.

## 3. Structured data (JSON-LD)

This is the highest-value part for actual search appearance (rich snippets), and it has a direct
dependency on a feature already built this session: the reviews system now gives every product a
real rating aggregate.

- **Product pages:** `Product` schema - name, image, price/availability (from the CRM, same as
  today's product pages already fetch), plus `AggregateRating` (`ratingValue`, `reviewCount`) -
  pull this from `GET /api/reviews?productId=` (`src/app/api/reviews/route.js`), which already
  returns exactly `{ aggregate: { count, average } }` for approved reviews only. If `count` is 0,
  omit `AggregateRating` entirely - an empty/zero rating block is worse than none, and Google's
  own guidelines say not to mark up a rating that doesn't exist yet.
- **Category pages:** `BreadcrumbList` schema.
- **Homepage:** `Organization` / `WebSite` schema (name, logo, social links - these are static,
  don't need admin editing, just get hardcoded in the frontend).

Whether this JSON-LD is generated by the storefront (recommended - it already has the live
price/stock data on the page) using SEO fields fetched from this backend, or assembled entirely
here and served as a ready-made `<script type="application/ld+json">` blob, is an implementation
choice - the former is more standard for a Next.js site and avoids this backend needing to know
the storefront's exact rendering format.

## 4. API endpoints (follow existing conventions exactly)

Mirror `src/app/api/reviews/route.js` and `src/app/api/product-images/route.js` for the pattern:
`force-dynamic`, `checkAdminToken` from `src/lib/adminAuth.js` for writes, public GET for reads.

- `GET /api/seo-meta?entityType=product&entityId=138` - public, one entity's SEO fields (or
  `{}`/defaults if none saved yet - "no override" is a normal state, not an error, same as
  `product_content`'s GET).
- `PUT /api/seo-meta` - admin-gated, upsert one entity's row (body: `entityType`, `entityId`, plus
  the fields). One endpoint for all three entity types, not three separate ones.
- `GET /api/seo-meta/sitemap-urls` - public, returns every indexable URL this backend knows about
  with a `lastmod`: every `product_index` row with `status = 'active'` (see
  `src/lib/productIndexSync.js` for that table), plus every category/page row that has
  `is_noindex = 0`. **This does not serve `sitemap.xml` itself** - the storefront calls this,
  builds the actual sitemap at its own domain (Next.js's built-in `app/sitemap.js` support), and
  serves it from `shopq.lk` where Google expects it for that domain.

## 5. Admin UI

Two things, not one:

1. **Per-product tab/section** on the existing Products page (`src/app/admin/product-content/page.js`)
   - alongside Features/Highlights/Images, add an "SEO" section with meta title (+ char counter),
   meta description (+ char counter), OG image (default to primary product photo, with an override
   field), canonical URL, and a noindex checkbox. Same save button, same pattern as the rest of
   that form.
2. **A separate `/admin/seo` page** for categories and static pages - these aren't tied to a single
   product's edit flow. List each known category/page with the same fields. **Before building
   this: get the actual list of categories and static routes from whoever knows the storefront's
   current sitemap** - this backend/session has no visibility into that project's routes.
